“我这里能跑”是一条有用的信息，可惜不是安装说明。

换台机器，原来的绝对路径没有了，管理员账号不该照搬，页面分享地址也不能还写着别人的域名。容器全部变绿之后，第一次发布仍可能卡在目录权限上。绿灯很好看，但它不负责替人补配置。

HADESD 当前支持一套部署对应一份博客内容，可以挂两个阅读前端。每个实例有自己的管理员、数据库、媒体和发布目录；它不是多租户博客平台。

## 从空机器开始，先走这三步

在仓库根目录运行：

```sh
./scripts/deploy.sh init --admin-user admin
./scripts/deploy.sh start
./scripts/deploy.sh bootstrap
```

宿主需要 Docker 和满足覆盖文件语法要求的 Compose。初始化所需的 Node 在容器中运行，不要求宿主另装 Node、pnpm 或 Java。

默认环境文件是 `.env.docker`；管理员密码和应用数据位于 `.local/docker/`。MySQL 和 Redis 使用当前 Compose 项目的持久卷。初始化不会打印密码或覆盖已有配置，`bootstrap` 只给新数据库使用。

随后登录后台、保存设置、写文章并发布。启动成功不会自动替你生成公开内容。若运行多个实例，环境文件、Compose 项目名、数据目录和端口都要分开；只改项目名，不会自动隔开两个 Worker 写入的宿主目录。

## 先把别人的名字和域名换掉

HADESD 是软件名称，博客站名、介绍和文章属于使用者。共享后台设置随发布快照生效；阅读站的名称和首屏说明还可以在 `apps/journal/app/site.ts` 调整，修改后同样需要重新构建发布。

旧实例升级还有个细节：以前可能从未真正保存过 `site_settings` 行，一直使用默认设置。V6 迁移会在缺少设置时，从仍保留的成功快照取回旧站身份；已有设置不覆盖，缺少开场标题的旧快照由前端兼容处理。否则一次升级，可能顺便把站长名字也升级成别人的。

域名用 `SITE_ORIGIN` 配置。它参与 canonical、Open Graph、RSS、sitemap、robots 和终端主机名。配置只接受 HTTP(S) origin，例如 `https://blog.example.com`，不接受账号、子路径、查询参数或 fragment；部署到 `/blog/` 子目录不是当前支持方式。

要增加普通阅读站，设置 `JOURNAL_SITE_ORIGIN`，使用不同主机名，并准备对应 DNS 和 TLS。两个前端共用内容、账号和发布快照，但 Cookie 按域名隔离，需要分别登录。仅换端口不符合当前双域名 Nginx 配置方式。

改好配置后要重建相关容器并发布。静态 HTML 不会因为环境文件更新，就自己把 canonical 擦掉重写。

## 权限报错，先别祭出 777

初始化把私有配置限制在根目录的 `.env` / `.env.*` 或 `.local/` 中，数据目录限定在 `.local/` 下。这些位置同时被 Git 和 Docker 构建忽略。

不是文件叫 `secret.txt`，它就知道该保密。若把凭据放进任意源码目录，而 Dockerfile 又复制整个仓库，文件权限 600 也挡不住拥有者把它带入镜像。

路径检查还覆盖派生目录：父目录没问题，不代表下面的 `media`、`published` 没有通过符号链接指向别处。初始化也检查目录、密码文件的类型，并保持 Docker bind mount 的宿主绝对路径正确。

应用容器使用初始化用户的 UID/GID 读写数据；Nginx 需要能遍历公开发布目录，私有媒体和密码则应保留更严的权限。`chmod -R 777` 能让一些报错消失，也能让目录原本的权限设计一起消失。

## 代理头不能靠“看起来像”来信任

HTTPS origin 会启用安全 Cookie，登录必须从 HTTPS 入口进行。反向代理还要正确转发公开协议、主机和真实访客地址：前两者影响同源判断，后者影响限流。

Nginx 按配置固定上游 Host、协议和端口，并清洗来客转发头。只有 `TRUSTED_PROXY_CIDRS` 中的来源，才允许提供用于恢复访客地址的信息。

填写的是内层 Nginx **实际看到的代理地址**，不是随手复制一段网段。完全不信，所有读者可能挤在同一个代理 IP 的限流额度里；全部都信，来客就能自己填地址绕过限制。转发头不是身份证，谁递过来的同样重要。

## 备份别只打包数据库

MySQL 保存账号、修订、评论和发布记录，媒体存储保存附件，发布目录保存静态文件、快照和 `current`。恢复时需要让它们对上同一版本。

一个可执行的顺序是：等待发布结束，暂停写作、上传和评论等写入；导出数据库，归档配置、媒体与发布目录；在隔离目录或新主机恢复；核对文章、附件、读者文件和 manifest，最后再开放流量。

Redis Session 通常可以丢弃，让用户重新登录。正文和图片可不能靠重新登录变回来。S3 模式还要备份数据库引用的对象，本地媒体目录不能替它交作业。

仓库的 `pnpm backup` 面向本地源码开发环境，完整 Docker 实例有自己的运维组合。使用前确认目标数据库与存储模式，不要仅凭命令里有个 “backup” 就放心执行。

## 哪些检查回答哪些问题

| 想知道什么 | 对应检查 |
| --- | --- |
| 路径解析、修订规则有没有回归 | 纯逻辑、组件与脚本测试 |
| 数据库事务、会话、对象存储能否配合 | 隔离的后端集成测试 |
| 手机上能否输入、滚动、点到链接 | 真实浏览器检查 |
| 备份文件是否真的能救场 | 在空环境恢复并核对 |

常规检查入口包括：

```sh
pnpm typecheck
pnpm test
node --test scripts/*.test.mjs
```

后端 `./gradlew test` 需要 Docker 和测试镜像；端到端测试需要隔离的数据与服务，包含写入、发布、撤稿，不能直接指向正式博客。

这些是检查方法，不是本文附赠的一张“全部通过”证明。真实 GPU、外部对象存储和公网 TLS 没有执行验证，就应在交付记录里保留这一限制。备份文件存在，也只说明文件存在；恢复过，才知道它是否能用。

安装与恢复细节见 `docs/self-hosting.md`、`docs/dual-frontends.md`。实现可对照 `scripts/setup.mjs`、`scripts/deploy.sh`、`scripts/nginx-config.mjs`、`scripts/trusted-proxies.mjs`、`infra/compose/compose.standalone.yaml` 和 `packages/contracts/src/site-origin.mjs`。
