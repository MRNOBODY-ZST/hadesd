一个项目在作者的机器上运行，并不意味着换一台机器也能运行。账号可能写死，页面元信息可能指向原域名，数据库和附件目录可能依赖某个用户的绝对路径。即使容器全部启动，第一次发布也可能因为目录权限而失败。

HADESD 的自托管入口围绕一个具体范围设计：一套部署对应一份博客内容，可以同时提供终端站和普通阅读站。每个实例有自己的配置、管理员、数据库、媒体和发布目录；这里没有建立多租户平台。

## 先把站点身份从软件名称中分离

HADESD 是软件名称，站点名称和作者介绍则是使用者的数据。后台可以保存站点名称、标语、个人简介、首页文案、开场标题、导航和外部链接。

这些设置随发布快照生效。这样既能独立审阅，也能与内容一起回滚。保存设置不会让一部分读者立即看到新首页，而其他静态页面还保留旧身份。

兼容旧站点时还需要处理一种不显眼的状态：以前的版本可能一直使用默认设置，从未真正保存过 `site_settings` 行。如果只修改应用默认值，下次发布就可能把原来的站点身份换掉。

当前新增迁移只在缺少设置行时，从已有成功且仍保留的快照中取回站点设置；已经保存的设置不会被覆盖。旧快照没有开场标题字段时，前端继续使用兼容回退。新安装才获得中性的初始文案。

## 域名是部署配置，不是文章内容

`SITE_ORIGIN` 表达公开站点的协议、主机和可选端口。它用于 canonical、Open Graph、RSS、sitemap、robots 和终端主机名。

域名不能分别散落在首页组件、RSS 脚本和发布 Worker 中。当前公开构建与发布使用共享的 origin 校验函数，并将结果写入页面 loader 数据，浏览器导航后也能继续生成相同域名的元信息。

地址只接受 HTTP 或 HTTPS origin，不接受账号、子路径、查询参数或 fragment。因此 `https://blog.example.com` 是有效的配置形态，整个站点部署到 `/blog/` 则不在当前支持范围内。

修改域名后要重建相关容器并重新发布。只编辑配置文件，不能自动改写已经生成的 HTML 中的 canonical。

## 第二个域名共用内容，而不是再装一个博客

普通阅读前端放在 `apps/journal`。它由可选的 `JOURNAL_SITE_ORIGIN` 启用，例如终端站使用 `https://blog.example.com`，普通阅读站使用 `https://journal.example.com`。两个配置必须使用不同主机名；将同一主机改成另一个端口不属于当前 Nginx 双域名入口的配置方式。

两个前端共用数据库、媒体、账号和发布快照。Worker 先构建终端站，再构建普通阅读站，检查两套完整产物后才切换同一个 `current`。因此增加一个阅读站不需要复制文章，也不需要重新创建账号。

浏览器会话不会因此跨域共享。两个域名各自通过自己的 `/api/` 入口访问相同后端，用户在两个站点分别登录；Cookie 不被扩展成跨域凭据，系统也没有实现 SSO。

启用第二域名时，要在实例配置中设置 `JOURNAL_SITE_ORIGIN`，为它配置 DNS 和 TLS，并重建入口与 Worker 后重新发布。两个站点各自使用自己的 canonical、Open Graph、RSS 和 sitemap。若开启安全 Cookie，两个公开入口都应使用 HTTPS。

## 最短安装路径要能解释数据存在哪里

新安装的 Docker 入口是：

```sh
./scripts/deploy.sh init --admin-user admin
./scripts/deploy.sh start
./scripts/deploy.sh bootstrap
```

这些命令从仓库根目录执行。宿主需要 Docker 和满足覆盖文件要求的 Compose，初始化所需的 Node 在容器内运行，宿主不必另外安装 Node、pnpm 或 Java。

默认配置写入 `.env.docker`，管理员密码和应用数据放在 `.local/docker/`。数据库和 Redis 使用该 Compose 项目的持久卷。初始化不会打印密码，也不会覆盖已有配置；`bootstrap` 只用于新数据库。

启动容器并不会自动创建公开内容。管理员还需要在后台保存设置、创建文章并发布，Worker 才会生成公开版本。

如果需要多个实例，环境文件、Compose 项目名、数据目录和监听端口都要独立。仅改项目名仍可能让两个发布器写入同一个宿主目录。

## 目录边界是功能正确性的一部分

初始化限定配置文件位于根目录的 `.env` / `.env.*`，或 `.local/` 内；数据目录限定在 `.local/` 下。这些位置同时受 Git 和 Docker 构建忽略规则保护。

原因很实际：如果允许把密码写到任意 `config/local.env`，而镜像构建又复制整个源码目录，凭据就可能进入构建上下文乃至镜像。文件权限为 600 也不能阻止构建工具以拥有者身份读走它。

路径检查还必须覆盖派生目录。只确认 `.local/docker` 不是符号链接，不代表它下面的 `media` 或 `published` 没有指向别处。当前初始化在创建文件前检查这些派生路径，并要求目录和密码文件具有正确类型。

Docker 初始化把仓库挂载到容器中的相同绝对路径。因此写入配置的 bind mount 路径在宿主仍然成立，而不是指向一次性容器中的临时目录。

应用容器使用初始化用户的 UID/GID 读写数据；公开发布根目录需要允许 Nginx 遍历，私有媒体和密码则保留更严格权限。把整个目录改成全局可写，只会掩盖权限设计没有完成。

## HTTPS 同时影响登录和图片

HTTPS 部署需要自己的 TLS 入口与证书。初始化时填写公开 HTTPS origin，会启用安全 Cookie；随后必须从 HTTPS 地址登录。

反向代理还要明确两类信息：公开请求的协议与主机，以及真实访客的地址。前者影响同源判断，后者影响限流。

独立 Nginx 根据配置固定上游 Host、协议和端口，并清洗客户端传来的转发头。对于真实访客 IP，默认不信任 `X-Forwarded-For`；只有显式列入 `TRUSTED_PROXY_CIDRS` 的代理来源，才允许通过 Nginx 的 real-ip 规则恢复访客地址。

TLS 入口必须用实际连接地址覆盖转发头，不能直接相信浏览器给出的值。可信来源也应按内层 Nginx 实际看到的地址配置，不能照搬另一台服务器的网段，更不能把所有来源都标为可信。

没有这一步，所有访客可能共享一个代理地址的限流额度；盲目信任所有转发头，则会让客户端自行挑选地址绕过限流。两种错误需要分别避免。

## 备份必须能重建同一个公开版本

完整内容不只存在于数据库。MySQL 保存账号、修订、评论和发布记录；媒体目录保存原始附件；发布目录保存静态产物、快照和当前指针。三者需要来自同一个维护窗口。

一个可操作的恢复顺序是：

1. 等待活动发布结束，暂停写作、上传、评论和发布等写入。
2. 导出数据库，并归档配置、媒体和发布目录；备份本身按私有数据保护。
3. 在独立目录或新主机中准备空数据库，先恢复数据，再启动后端迁移和应用。
4. 核对文章、公开版本、附件和读者文件，然后才开放流量。

Redis 会话通常可以舍弃并重新登录，但不能用它替代正文备份。S3 模式还需要备份数据库引用的对象，本地媒体目录归档不能代替对象存储导出。

仓库中本地源码开发的 `pnpm backup` 与完整 Docker 实例有不同的目标环境。运维命令必须与当前部署组合对应，不能看到“backup”这个名字就直接用于另一个数据库。

## 验证要分层，也要写明没有验证什么

这个项目的验证入口分别覆盖不同问题：

| 层级 | 典型检查 | 能证明什么 |
| --- | --- | --- |
| 纯逻辑与组件测试 | 路径解析、补全、设置字段、动画阶段 | 固定输入下的行为约束 |
| 脚本测试 | 初始化、路径拒绝、域名校验、代理配置 | 文件与配置边界 |
| 后端集成测试 | 临时 MySQL、Redis、MinIO | 事务、权限和真实协议协作 |
| 浏览器验证 | 桌面/手机、中文输入、导航、GPU 回退 | 用户可观察的交互结果 |
| 恢复演练 | 空库恢复、文件校验、manifest 对齐 | 备份是否真正可用 |

常规开发可以从下面几项开始：

```sh
pnpm typecheck
pnpm test
node --test scripts/*.test.mjs
cd backend
./gradlew test
```

后端集成测试需要 Docker 及测试所需镜像。浏览器端到端测试则需要另行准备隔离的数据和服务；其中包含真实写入、发布和撤稿，不能指向正式站点。

测试存在，不代表这一轮已经执行通过。文章也不把某次历史报告中的数量、截图或软件渲染成绩当作当前机器的验收结果。每次交付应留下实际执行命令、结果和范围；真实 GPU 性能、云桶连接或外部 TLS 没有验证，就明确保留这个边界。

可自行部署最终是一种交付能力：另一位使用者能找到自己的配置，知道数据在哪里，理解更新何时生效，并在出错后把站点恢复回来。
