设想这样一个场面：文章还在构建，作者又保存了一次；Worker 随后重启；读者的标签页则停留在上一版。

三个参与者各忙各的，都没有做错。可如果发布脚本每次都读取“最新内容”，网站就可能拼出一份谁也没审过的稿子：旧标题、新正文，再配一个更晚保存的摘要。

这里需要的不是更快地复制文件，而是先说清楚：这次到底发布哪一份。

## 先点菜，再开火

假设线上是 A1 和 B3，后台已经保存了 A2、B4。作者选择发布 A2，候选版本应当是 **A2 + B3**。B4 还没被选中，不能因为刚好坐在数据库里，就搭上这班车。

普通发布请求带着 `contentId` 和 `revisionId`。后端检查修订归属，把指定修订放进当前公开内容集合，再冻结站点设置、搜索投影和媒体引用。

`ReleaseService` 在事务内完成这些操作。当前实现用 `publisher_lock` 单行锁串行安排发布，已有活动任务时拒绝新任务。它服务的是一套博客，不是一个需要同时给几千个租户排班的平台。

![冻结快照之后依次构建两个前端；全部校验通过才切换 current，任一构建失败则继续提供旧版本](/editorial/publishing-v1.png)

*示意图中的“保持旧版”指切换前失败；切换后的回报故障，需要下面提到的对账机制。*

站点设置也在快照里。普通发布、撤稿和单独发布设置会采用已保存设置；回滚则采用目标快照中的设置。改文章时顺手改了站点标题，发布前也应一起核对。

## Worker 不是领了任务就能永久上岗

任务状态大致是：

```text
QUEUED → BUILDING → READY → DEPLOYING → SUCCEEDED
```

失败会进入 `FAILED`。Worker 领取任务时获得租约和 `leaseToken`，之后持续发送心跳；代码当前是每 15 秒心跳一次，服务端租约期限 120 秒。这些是实现参数，不是性能测量结果。

失去心跳会触发构建取消，切换前还要再确认租约。超时任务可以重新领取，新领取会更新令牌，并限制反复领取次数。旧进程不能凭一张过期工牌继续汇报状态。

租约解决“谁有权推进任务”，并没有把数据库和文件系统合成一个事务。这个区别后面很重要。

## 两个前端，都得交卷

Worker 只使用冻结快照，执行固定的构建命令：

```sh
pnpm --filter @hadesd/web build
# 配置 JOURNAL_SITE_ORIGIN 时，还会构建阅读站
pnpm --filter @hadesd/journal build
```

快照路径、输出目录和各自的公开 origin 通过环境变量提供；进程使用 `shell: false`，文章标题和正文不会拼进 Shell 命令。

退出码为 0 只是第一关。发布器还会检查公开路由、重复地址、路径穿越、缺页、HTML 完整性、符号链接、产物数量和总大小。双站还要核对 canonical 与 Open Graph URL，避免打开阅读站，分享地址却跑回终端域名。

两套产物都通过，才写完成标记。第二个前端缺页时，第一个即便已经构建完，也不会单独上线。系统还会移除 SPA fallback，避免不存在的文章返回一个假装成功的页面；HTML 的内联脚本则通过构建后计算的哈希加入 CSP。

## 真正换站，只动一个指针

```text
published/
├─ current → releases/旧版本
├─ releases/
│  ├─ 旧版本/
│  └─ 新版本/
│     ├─ manifest.json
│     ├─ snapshot.json
│     ├─ site/
│     └─ journal/
├─ assets/
└─ journal-assets/
```

产物先在 staging 准备，再移入 releases。Worker 创建指向新版本的临时相对符号链接，用 `rename` 替换 `current`。

两个域名读取 `current/site` 和 `current/journal`，因此只需切换一次。依赖同一文件系统的原子重命名语义，入口看到的是旧指针或新指针，不是“首页已更新，文章还在搬家”。不要把这些目录拆到无法完成同样原子操作的不同文件系统。

这里的“原子”有范围：原子的是指针替换，不是一名读者后续所有请求。浏览器可能先拿到旧 HTML，再向新版本 API 发请求。

带旧 `releaseId` 的公开请求会得到 `409 RELEASE_CHANGED`，需要刷新。终端按内容 ID 读取正文时还检查修订 ID。带哈希的脚本资源分别保留在共享资源目录，减少旧标签页立刻丢失脚本的情况，但不保证旧页面永远兼容新 API。

## 站已经换了，成功消息却没送到

如果 Worker 切换 `current` 后退出，来不及汇报 `SUCCEEDED`，线上实际上已经更新。此时应依据 `current/manifest.json` 对账，而不是因为数据库还写着“正在发布”，就认定什么都没发生。

Worker 和后端都有相应检查。后端只读发布目录，Worker 才有切换权限；公开查询围绕当前可见版本，内部候选快照不会提前放给读者。

撤稿与回滚也走发布流程。撤稿生成不含目标内容的新快照；回滚读取保留的旧快照，分配新发布 ID，重新构建与校验，不改写作者的最新草稿。已经被下载或复制的内容，撤稿当然收不回来。

当前保留策略保护当前版本、最近五个成功历史版本和活动任务。过期正文快照会清理，不能把资源目录还留着旧脚本，误认为所有旧文章都能无限回滚。

## 别只测试顺利的时候

可以刻意少生成一个文章页面，或者让第二个前端带上错误域名，检查 `current` 是否仍指向旧版。再分别验证：构建期间保存草稿不会改变候选输入，过期令牌不能推进任务，切换后丢失成功回报能对账，清理器不会删除当前目录。

这些检查针对不同故障。一次首页截图再漂亮，也不能代替它们。
