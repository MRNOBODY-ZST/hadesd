假设一篇文章正在发布。前端构建到一半，作者又保存了一个新草稿；随后 Worker 重启，而读者还开着上一版页面。系统到底应该公开哪一份文字？

只把“最新内容”交给构建脚本，无法回答这个问题。HADESD 使用不可变修订、冻结快照和一个公开版本指针，让每一步都有可检查的输入和结果。

## 发布请求必须指明修订

文章身份由 `contentId` 表达，一次保存由 `revisionId` 表达。普通发布需要同时提供这两个标识。服务端先确认修订属于目标内容，再把它替换进当前公开内容集合。

例如当前公开集合是：

```text
文章 A → 修订 A1
文章 B → 修订 B3
```

发布 A2 后，候选集合成为 A2 与 B3。即使 B 的后台已经保存了 B4，也不会顺带把 B4 公开。发布的单位是明确选择的修订，不是数据库中此刻所有最新行。

站点设置也随快照冻结。单独发布设置时，系统保留当前公开内容修订，采用已保存的新设置；普通发布和撤稿也会读取已保存设置。回滚则恢复目标快照中的内容和设置。

## 冻结时一起确定可检索内容

`ReleaseService` 在创建任务时取得发布锁，并在事务内生成快照、发布条目、搜索投影与媒体引用。快照包括发布 ID、创建时间、站点设置和明确的公开内容集合。

这份 JSON 既是构建输入，也是后端解释该版本的依据。Worker 不需要在构建过程中反复查询“最新文章”，因此不会出现首页读取旧标题、正文读取新段落、RSS 又读取另一版摘要的拼接结果。

当前实现使用 `publisher_lock` 单行事务锁，并拒绝在已有活动发布任务时创建另一项任务。这是面向单站点的简化：先把发布顺序做明确，再考虑更复杂的并发调度。

## Worker 用租约领取工作

任务主要经过这些状态：

```text
QUEUED → BUILDING → READY → DEPLOYING → SUCCEEDED
                      失败可进入 FAILED
```

领取任务后，Worker 获得有时限的租约和 `leaseToken`。当前代码每 15 秒发送一次心跳，服务端租约期限为 120 秒。Worker 汇报状态时必须携带对应令牌，旧进程不能仅凭任务 ID 继续推进状态。

心跳失败会触发构建取消。切换发布指针前，Worker 还会做最后一次租约确认。后端支持超时任务重新领取，新的领取会更新令牌，并限制反复领取次数。

租约解决的是“谁仍被允许推进这个任务”，不是把文件系统和数据库变成同一个事务。切换指针与回报成功之间仍然存在故障窗口，所以还需要对账机制。

## 构建阶段只消费冻结输入

Worker 将快照写到独立工作目录，然后执行固定命令：

```text
pnpm --filter @hadesd/web build
```

如果配置了 `JOURNAL_SITE_ORIGIN`，还会执行 `pnpm --filter @hadesd/journal build`。两个构建使用同一个快照文件、各自的公开 origin 和独立输出目录，分别生成终端界面与普通阅读界面。

快照路径和构建目录通过环境变量提供，命令使用 `shell: false` 启动。标题、slug 和正文不会被拼接进 Shell 命令。

React Router 在构建时读取快照，为每个公开路由生成静态页面。生产请求随后读取这些文件，不需要为每个读者启动 Node 服务端渲染。

构建成功仍不等于可以上线。发布准备阶段还会校验：

- 路由是否位于允许的公开命名空间，是否重复或包含路径穿越。
- 每个计划路由是否真的产生了完整 HTML 文件。
- 产物内是否出现符号链接，文件数量和总大小是否超过限制。
- 发布清单中的 ID 是否与任务一致。

双前端发布还会检查每个路由的 canonical 和 Open Graph URL 是否属于该前端的 origin。只有两套产物都完成校验，才写入完成标记；普通阅读站构建失败时，终端站也不会单独切换到新版本。

React Router 生成的 SPA fallback 会被移除，防止不存在的公开文章被悄悄返回成成功页面。HTML 还会加入内容安全策略，内联脚本通过构建后计算的哈希授权。

## 原子切换发生在哪里

发布目录可简化为：

```text
published/
├─ current → releases/版本甲
├─ releases/
│  ├─ 版本甲/
│  │  ├─ manifest.json
│  │  ├─ snapshot.json
│  │  ├─ site/
│  │  └─ journal/       # 可选的普通阅读站
│  └─ 版本乙/
├─ assets/
├─ journal-assets/     # 普通阅读站的哈希资源
├─ staging/
└─ work/
```

校验通过后，Worker 将 staging 中的版本移入不可变的 releases 目录，准备一个指向新版本的临时相对符号链接，再通过 `rename` 替换 `current`。

这些目录位于同一个发布根目录中。依赖文件系统的原子重命名语义，入口会看到旧指针或新指针，而不是逐个覆盖文件过程中的半套站点。部署时不应把 staging、releases 和 current 分散到无法进行相同原子操作的不同文件系统。

两个域名分别读取 `current/site` 与 `current/journal`，所以不需要协调两次独立上线。一次 `current` 切换就决定了两种阅读界面的公开版本。

原子的是指针替换，不是“一名读者的所有后续请求都锁定一个版本”。浏览器仍可能在切换前取得旧 HTML，在切换后发出下一次 API 请求。这是另一层需要处理的问题。

## 用 manifest 对账，而不是只相信成功消息

`current/manifest.json` 是当前可见版本的权威。后端只读发布目录，Worker 才能写入和切换。

如果 Worker 已切换 `current`，却在发送 `SUCCEEDED` 前退出，公开站实际上已经更新。重新运行时，Worker 会先检查当前指针；后端也有依据 manifest 修正任务状态的对账路径。

反过来，任务数据库里显示正在构建，并不表示读者应该提前访问那份快照。内部快照接口与公开接口分离，公开查询始终围绕当前可见发布进行。

对于带有旧 `releaseId` 的公开请求，服务端返回 `409 RELEASE_CHANGED`，让客户端刷新。终端按内容 ID 读取正文时还检查返回的修订 ID，避免在旧目录中无声显示新版本正文。

## 撤稿与回滚也是发布

撤稿通过生成一个不含目标内容的新快照实现。指针切换后，静态路由、公开搜索和附件引用随当前版本更新。已经被读者下载或复制的内容当然无法收回，发布边界只能控制此后由本站提供的访问。

回滚也生成新的发布 ID，使用目标保留快照中的内容和设置，并重新走构建、校验与切换流程。它不是把最新草稿改写为旧文字，也不是绕开权限直接移动任意历史目录。

保留策略维护当前版本和最近五个成功历史版本，并保护活动任务。过期版本的正文快照与相应投影会被清理，不能再用于回滚。

同时，带哈希的代码资源分别保留在共享 `assets` 与 `journal-assets` 目录，以减少旧标签页因为脚本文件消失而立即失效的情况。这个兼容措施不保留无限历史正文，也不承诺旧页面能一直使用当前动态 API。

## 如何验证，而不只看“发布成功”

发布测试最有价值的断言是失败时没有跨过边界。例如：

| 制造的条件 | 应检查的结果 |
| --- | --- |
| 少生成一个文章页面 | 校验失败，`current` 仍指向旧版本 |
| 第二前端缺页或生成错误域名的 canonical | 两种阅读界面都继续提供旧版本 |
| 发布过程中保存新草稿 | 候选快照仍使用指定修订 |
| 旧 Worker 使用过期令牌回报 | 服务端拒绝推进状态 |
| 切换完成后成功回报中断 | 能依据 manifest 对账 |
| 清理名单意外包含当前版本 | 清理器再次检查并保留当前目录 |

仓库的发布器测试和后端集成测试围绕这些边界建立。它们比一张成功页面截图更接近发布系统真正需要承担的责任。

## 对照源码阅读

- `backend/src/main/java/sh/hades/daemon/release/ReleaseService.java`：冻结、任务状态、租约、对账与保留策略。
- `backend/src/main/java/sh/hades/daemon/release/CurrentRelease.java`：当前 manifest 的读取。
- `apps/publisher/src/worker.mjs`：任务领取、构建进程与心跳。
- `apps/publisher/src/release.mjs`：路由校验、产物检查、原子指针与历史清理。
- `apps/publisher/test/release.test.mjs`：产物失败与版本切换回归。
- `backend/src/test/java/sh/hades/daemon/DaemonApplicationTests.java`：发布生命周期的集成断言。
